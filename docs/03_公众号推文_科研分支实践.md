### 【开头】为什么要做一个MC模组管理工具？

各位关注我的朋友，都是冲着「从零搭建认知智能大模型」这个系列来的。
但可能很多人都有一个疑问：**学了那么多大模型、Agent、RAG的知识，然后呢？**
是不是除了写Demo、搭Chatbot、跑开源模型，就没别的落地方式了？

我的答案是：**不是的。**

这次我想跟大家分享一个我刚完成的项目：
**MC全生态智能适配工程师**，一款 Minecraft 模组环境智能管理工具。
它不是什么高大上的产品，甚至目标用户群非常小众（MC模组玩家），
但它是一个**完整的、可变现的、由Agent驱动的垂直工具产品**。

做这个项目的初衷很简单：
我自己玩MC装模组的时候，发现模组搜索下载、版本兼容、Mixin冲突排查、跨版本迁移这些事情，繁琐、重复、又极度依赖经验判断。
而这些**「依赖经验判断的重复性工作」，恰恰是Agent最擅长的场景。**

于是我花了大约60天的业余时间，从零把它做了出来。
今天这篇文章，我想把整个过程分享给大家，包括：
- 为什么选 MC 模组这个赛道
- 产品的10个核心功能是如何设计的
- 如何用 Python + Agent 思维构建核心算法
- 付费授权体系是如何设计的（60天免费 → 会员 → 按次付费）
- 以及最重要的：**这个项目如何帮我验证「自给自足搭建大模型」的可行性**

### 【一】选赛道：为什么是 Minecraft 模组管理？

做垂直工具，第一步就是选赛道。
我当时有几个备选方向，最后选了 MC 模组，原因有三个：

**1. 痛点真实且高频**
MC模组玩家几乎都经历过这些：
- 找一个模组的特定版本，翻遍CurseForge、Modrinth、各种论坛
- 装了几十个模组，进游戏闪退，排查Mixin冲突排查一整天
- MC版本更新，所有模组要重新找对应版本，一个个测试兼容性
- 想把某个模组从Forge迁到Fabric，完全不知道从何下手

这些痛点不是伪需求，是每天都在发生的事情。

**2. 目标用户付费意愿明确**
愿意玩模组服的MC玩家，本身就是对游戏体验有更高追求的一群人。
他们愿意花时间研究整合包、愿意花几十块买整合包、愿意花几百块开服务器。
对一个能帮他们省时间、少踩坑的工具，几块到几十块的定价是完全可以接受的。

**3. 技术栈匹配，不需要机器学习**
很多人一想到「AI工具」就想到要训模型、要数据集、要GPU。
但这个项目完全不需要。
模组版本兼容是规则明确的查表问题、Mixin冲突是静态代码分析问题、崩溃日志是模式匹配问题。
这些用**传统算法 + 领域知识库**就能很好地解决，
Agent的价值在于**把这些能力编排成用户能理解的自然语言输出**，
而不是去端到端地解决问题。

这一点非常重要，后面我会专门讲。

### 【二】产品设计：10个功能是怎么来的？

做任何工具，功能都不是拍脑袋想出来的，而是从用户的「操作链路」里拆出来的。

一个MC模组玩家从0到1搭好一个整合包，链路是这样的：

```
确定MC版本+加载器 → 找模组 → 下载模组 → 检测冲突 → 进游戏测试
        ↓                                            ↓
   需要汉化                                 崩溃了？修复
        ↓                                            ↓
   汉化语言文件                          修复不了？升级/换模组
        ↓                                            ↓
   存档备份                        以后想换版本？移植评估
```

把链路里每一步的痛点拆出来，就是功能：

| 链路环节 | 痛点 | 对应功能 |
|---------|------|---------|
| 找模组前 | 不知道选什么版本组合 | F3 环境引导搭建 |
| 拿到模组 | 不知道依赖信息 | F1 JAR结构解析 |
| 找模组+下载 | 一个个找太麻烦 | F2 模组检索下载 |
| 装模组前 | 不知道会不会冲突 | F4 Mixin冲突扫描 |
| 定制资源 | 想改资源文件 | F5 资源重打包 |
| 玩游戏中 | 怕存档丢了 | F6 存档同步 |
| 玩模组时 | 英文看不懂 | F7 基础汉化 |
| 崩溃了 | 日志看不懂 | F8 报错修复 |
| 修不好 | 不知道怎么换 | F8.1 自动修复 |
| 想换版本 | 不知道能不能迁 | F9 移植可行性评估 |

这就是10个功能的来源。
不是我想做10个功能，是用户从0到1走完一条链路，**正好需要这10步**。

这种设计思路，我把它叫做「**链路拆解法**」。
先把用户的完整操作链路画出来，再给每个环节找痛点，最后给每个痛点对应一个功能。
这样做出来的产品，用户一用就觉得「这个工具懂我」。

### 【三】技术实现：Agent 思维 + 传统算法 = 降本增效

这一部分可能是大家最关心的：
**这个工具里到底有多少是真正的「AI/Agent」，有多少是硬编码？**

我的答案可能会让你意外：**核心算法90%是传统代码，Agent思维体现在另外10%里。**

举两个例子。

#### 例子1：F9 移植可行性评估

很多人看到「评估」两个字就觉得要上大模型。
其实不需要。我是这么做的：

1. **建立知识矩阵**：
   - 加载器迁移矩阵：Forge→NeoForge兼容性多少？关键变更点是什么？预估工作量？
   - 版本变化矩阵：1.20→1.21有哪些API变了？影响哪些模组？
   - 依赖支持表：某个模组在目标版本+加载器下有没有对应版本？
   这些都是可以人工整理的结构化数据。

2. **静态扫描**：
   - 扫模组的Mixin配置文件，看它注入了哪些类和方法
   - 如果注入的目标类在新版本被改名/删除了，就是风险点

3. **加权评分**：
   - 加载器兼容性：30%权重
   - 版本兼容性：25%权重
   - 依赖支持度：25%权重
   - Mixin复杂度：20%权重
   加权求和，得出0-100分，再划分风险等级。

整个过程没有调用任何LLM，全是规则+查表+统计。
但输出给用户的是一份「像AI写的」完整评估报告，
包含风险等级、评分、具体风险点、预估工作量、迁移建议——
这些结构化内容一旦用自然语言模板渲染出来，用户就会觉得「很智能」。

**这就是Agent思维的核心：不是让大模型去算，而是让系统以「对人类友好」的方式输出结果。**

#### 例子2：F8 报错修复

崩溃日志分析听起来很AI，其实也是模式匹配：
- Java异常栈里的常见错误模式有上百种
- 每种模式对应一组可能的原因和修复方案
- 把日志文本丢进规则引擎，匹配到模式就输出方案
- 命中多个模式时，按置信度排序，给用户Top3建议

当然，这里可以接入LLM作为兜底——
规则没匹配到的时候，再调大模型去理解日志内容。
但在V1版本，我发现80%的常见崩溃都能被规则覆盖，
上LLM反而增加了响应时间和成本。

**总结一下这套技术路线的哲学：**
> 能规则解决的，不要上模型；
> 能查表解决的，不要上推理；
> 模型只用在「最后一公里」的自然语言生成和兜底上。

这样做的好处是：
- 成本极低：V1上线后几乎没有API调用成本
- 速度快：所有功能毫秒级响应
- 可解释：每一条建议都能追溯到具体规则，不是黑盒
- 稳定：不会因为大模型幻觉给出错误建议

对于想做「自给自足」小工具的独立开发者来说，
这套方法论比「全链路大模型」靠谱100倍。

### 【四】商业模式：60天免费 → 会员 → 按次付费，是怎么设计的？

产品做完了，怎么赚钱？

我设计的是三层付费体系：

**第一层：60天免费期（拉新）**
- 用户首次使用自动计算，免费期60天
- 60天内除F9移植评估外，所有功能不限次
- F9首次免费，之后每天1次

为什么是60天？
- 太短（7天/14天）用户刚用出感觉就过期了，付费意愿低
- 太长（180天/1年）用户没有紧迫感，转化效率差
- 60天刚好够用户用完一整个MC版本周期（从搭整合包到玩腻），
  下个版本想继续用就会付费

**第二层：订阅会员（核心收入）**
- 单月/连续包月：8.88元/月
- 包季：23.88元/季（省2.76）
- 包年：88.88元/年（省17.68）

定价为什么这么低？
- 目标用户是学生党和年轻玩家，价格敏感度高
- 低门槛（一杯奶茶钱）会大幅提升转化率
- MC模组是长期需求，只要持续更新，续费率有保障
- 低价策略也能建立口碑，用户愿意推荐给朋友

**第三层：单次按需付费（补充收入）**
- 移植评估：9.9元/次
- 浅层适配：49.9元/次
- 深度诊断：89.9元/次
- 崩溃修复：39.9元/次

按次付费是给「临时有需求、不想订阅」的用户准备的。
比如某个玩家半年才迁一次模组版本，他不会开月卡，
但花9.9元买一次移植评估，节省几个小时的踩坑时间，是非常划算的。

### 【五】为什么说这验证了「自给自足搭建大模型」的可行性？

回到最开始的话题：为什么我作为一个「从零搭建认知智能大模型」的作者，
会花时间做一个MC工具？

因为我需要验证一件事情：**当我有了大模型和Agent的能力后，我能不能独立地把它变成一个能赚钱的产品？**

做这个项目的过程中，我验证了以下几点：

**1. 产品能力闭环**
从需求分析 → 产品设计 → 代码实现 → 打包发布 → 付费体系 → 推广渠道，
我一个人走完了完整的产品生命周期。
这意味着以后任何赛道，只要我能找到痛点，我都能以同样的方法论快速落地。

**2. Agent 技术的可迁移性**
移植评估的知识库+评分体系、报错修复的模式匹配、
Mixin冲突的静态分析——这些核心能力换个赛道依然成立。
换个行业（比如Excel自动化、PDF处理、论文格式检查），
只需要替换知识库和规则，就又是一个新产品。

**3. 正向现金流的可复制性**
只要产品解决了真实痛点，定价合理，
哪怕用户群再小众，也能获得正向现金流。
而正向现金流是「自给自足」的核心——
有了收入，你就不需要找工作、不需要融资，
可以用收入继续投资GPU、继续训练你自己的大模型，
形成一个**技术 → 产品 → 收入 → 更多技术**的正循环。

这也是我想通过这个系列传达给大家的核心理念：
> 大模型不是终点，而是工具。
> 学会用它解决真实世界里的小问题，
> 把每一个小问题变成一个能赚钱的小产品，
> 你就真的「自给自足」了。
